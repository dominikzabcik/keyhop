# Claude Code, Codex CLI, and GitHub Copilot: auth, transcripts, and quotas (3 October 2026)

Notes for a switcher that rewrites local logins and must not revoke tokens. Docs below were fetched on 3 October 2026 unless a source carries its own date. Older material is marked.

## Did Claude Code move credentials, add new account types, or change transcript paths or limit fields in 2026?

### Takeaway
The OAuth blob Keyhop swaps is still the documented store (`claudeAiOauth` in the macOS Keychain, or `~/.claude/.credentials.json` on Linux and Windows), and transcripts are still JSONL under `~/.claude/projects/`. 2026 docs add several credentials that outrank that blob, a macOS file fallback, per-directory Keychain entries, a long-path transcript rename, a separate Opus limit, usage credits, and a separate Agent SDK credit pool.

### Cited Findings
- Credential locations, current authentication page: macOS uses the encrypted Keychain; if the Keychain rejects the write (locked Keychain over SSH is the example), Claude Code stores the login in `~/.claude/.credentials.json` mode `0600`, the same file Linux uses. Windows uses `%USERPROFILE%\.claude\.credentials.json`. `CLAUDE_CONFIG_DIR` moves `.credentials.json` under that directory, including the macOS fallback file, and keys the macOS Keychain entry to that directory so a different `CLAUDE_CONFIG_DIR` reads a different entry. The page does not print the Keychain service name. — [Authentication](https://code.claude.com/docs/en/authentication)
- Supported types on that page: claude.ai credentials, Claude API credentials, Microsoft Foundry Auth, Bedrock Auth, Vertex Auth, Anthropic profile and Workload Identity Federation credentials, and Claude apps gateway session tokens. Login methods listed: Claude Pro/Max, Teams/Enterprise, Claude Console (with or without an API key), cloud providers (Bedrock, Google Cloud's Agent Platform, Microsoft Foundry), and a self-hosted Claude apps gateway. — [Authentication](https://code.claude.com/docs/en/authentication)
- Precedence, highest first: cloud-provider env (`CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `CLAUDE_CODE_USE_FOUNDRY`), `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, `apiKeyHelper`, `CLAUDE_CODE_OAUTH_TOKEN`, then Anthropic profile / federation, then subscription OAuth from `/login`. A signed-in gateway session sits outside that list and outranks Bedrock, Vertex, and Foundry. — [Authentication](https://code.claude.com/docs/en/authentication)
- Official multi-account method is one `CLAUDE_CONFIG_DIR` per account (settings, session history, and claude.ai login or API key). Separate directories do not keep two Console sign-ins that have no API key apart, because that sign-in is stored outside the configuration directory. — [Authentication](https://code.claude.com/docs/en/authentication)
- Keyless Console sign-in requires Claude Code v2.1.242 or later. The recommended path stores the OAuth login as an Anthropic profile and creates no API key. The legacy path creates a Console API key and stores it with the other credentials. After a keyless Console sign-in, Claude Code signs the machine out of any claude.ai login. `/logout` removes and revokes the credential that sign-in wrote. Profiles live in `~/.config/anthropic` on macOS and Linux, or `%APPDATA%\Anthropic` on Windows. A named `ANTHROPIC_PROFILE`, or federation env vars, rank above `/login`. An active `user_oauth` profile ranks below a working `/login`. — [Authentication](https://code.claude.com/docs/en/authentication)
- `claude setup-token` prints a one-year OAuth token and does not save it. Set `CLAUDE_CODE_OAUTH_TOKEN`. It authenticates as the Claude subscription, is inference-only, and beats subscription OAuth from `/login`. `/login` while the variable is set switches the current session, and every new session reads the variable again until it is removed from the shell or a settings `env` block. — [Authentication](https://code.claude.com/docs/en/authentication)
- Bedrock and Vertex can be chosen as "3rd-party platform" at the login prompt. The Bedrock wizard saves the result to the `env` block of the user settings file (the Bedrock page does not name that file's path). Bedrock API keys are `AWS_BEARER_TOKEN_BEDROCK` with `CLAUDE_CODE_USE_BEDROCK=1`. Vertex/Agent Platform uses `CLAUDE_CODE_USE_VERTEX=1`; the Vertex page's `gcpAuthRefresh` example is in `~/.claude/settings.json`. Comparison table: Teams/Enterprise use Claude.ai SSO or email; Console uses an API key; Bedrock and "Claude Platform on AWS" use an API key or AWS credentials; Agent Platform (formerly Vertex AI) uses GCP credentials; Microsoft Foundry uses an API key or Microsoft Entra ID. — [Amazon Bedrock](https://code.claude.com/docs/en/amazon-bedrock); [Google Vertex AI](https://code.claude.com/docs/en/google-vertex-ai); [Bedrock, Vertex, and gateways](https://code.claude.com/docs/en/bedrock-vertex)
- `CLAUDE_CODE_OAUTH_TOKEN` "takes precedence over keychain-stored credentials" and is generated with `claude setup-token`. `CLAUDE_CODE_OAUTH_REFRESH_TOKEN` plus `CLAUDE_CODE_OAUTH_SCOPES` lets `claude auth login` exchange a refresh token without a browser. — [Environment variables](https://code.claude.com/docs/en/env-vars)
- 2026 bug reports still name the shared macOS item `Claude Code-credentials` and the field `claudeAiOauth`, with MCP tokens (`mcpOAuth`) in the same JSON blob. v2.1.136 fixed concurrent MCP OAuth writes that dropped `claudeAiOauth`. A later report describes a remaining race: concurrent refreshes of the single-use refresh token can persist blank `accessToken` and `refreshToken` with `expiresAt: 0`, leaving `subscriptionType` and `refreshTokenExpiresAt` intact. Recovery is an interactive `/login`. — [Issue 45551](https://github.com/anthropics/claude-code/issues/45551); [Issue 88583](https://github.com/anthropics/claude-code/issues/88583)
- Linux/Windows file still `~/.claude/.credentials.json`, field `claudeAiOauth`. v2.1.221 / 2.1.241 reports say a fresh login can write `expiresAt: 0` while `refreshTokenExpiresAt` is a future millisecond timestamp, so `claude auth status` reports `loggedIn: false`. Scopes in that report include `user:inference`, `user:mcp_servers`, `user:profile`, and `user:sessions:claude_code`. Changelog entries say a credential-save crash that corrupted `~/.claude/.credentials.json` was fixed, and a rare concurrent write that cleared a valid refresh token was fixed. — [Issue 83834](https://github.com/anthropics/claude-code/issues/83834); [Changelog](https://code.claude.com/docs/en/changelog)
- Transcripts: JSONL at `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`. The directory slug replaces every non-alphanumeric character with `-`. If that name exceeds 200 characters, Claude Code truncates to 200 and appends a hash of the full path. The line format is internal and "changes between versions." `CLAUDE_CONFIG_DIR` moves storage off `~/.claude`. `CLAUDE_CODE_PROJECT_DIR_NAME` (v2.1.234+, only honored when `CLAUDE_CONFIG_DIR` is also set) pins the project directory name. `CLAUDE_CODE_SKIP_PROMPT_HISTORY` suppresses transcript writes. `claude -p --no-session-persistence` suppresses one non-interactive run. Retention default is `cleanupPeriodDays` (30 days). Desktop and Cowork have a separate `desktopSessionCleanupPeriodDays`. — [Manage sessions](https://code.claude.com/docs/en/sessions)
- A 27 August 2026 issue says Claude Code 2.1.224 changed the encoding for paths over 200 characters, so tools that reimplemented the old slug resolve the wrong directory. The sessions page now documents the 200-character rule. Before v2.1.223, `claude --resume <id>` looked only in the current project and its git worktrees; it now searches other projects on the machine. — [Issue 90221](https://github.com/anthropics/claude-code/issues/90221); [Manage sessions](https://code.claude.com/docs/en/sessions)
- Status line `rate_limits`, documented for Claude.ai subscribers (Pro/Max) after the first API response: `five_hour` (5-hour rolling window) and `seven_day` (weekly). Each has `used_percentage` (0–100) and `resets_at` (Unix seconds). Either window may be absent. The documented schema has no Opus window, Sonnet window, or usage-credit object. — [Status line](https://code.claude.com/docs/en/statusline)
- Errors page: session and weekly limits are shared across models; an additional Opus limit applies only to Opus, so `/model` keeps working when that one is hit. Usage counts against session and weekly allowances at the same time. `/usage` shows plan limits and reset times. `/usage-credits` buys more usage on Pro and Max, or requests it from an admin on Team and Enterprise. — [Errors](https://code.claude.com/docs/en/errors)
- A 22 August 2026 report says the status-line `rate_limits` object is only `five_hour` and `seven_day`, and that with usage credits enabled the plan-limit percentage is not a hard stop. — [Issue 88781](https://github.com/anthropics/claude-code/issues/88781)
- IAM page callout: starting 15 June 2026, Agent SDK and `claude -p` usage on subscription plans draws from a monthly Agent SDK credit, separate from interactive usage limits. `claude -p` and Agent SDK sessions are stored, and they are omitted from the session picker and from `claude --continue`. — [IAM](https://code.claude.com/docs/en/iam); [Manage sessions](https://code.claude.com/docs/en/sessions)
- Policy, current legal page: OAuth is for purchasers of Claude Free, Pro, Max, Team, and Enterprise and for ordinary use of Claude Code and other native Anthropic apps. Third-party developers building products on Claude, including via the Agent SDK, are told to use an API key through Console or a cloud provider. Anthropic does not permit third-party developers to offer Claude.ai login or to route requests through Free, Pro, or Max credentials on behalf of their users. — [Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)

### Inferences
- Swapping `claudeAiOauth` in the default Keychain item still matches the subscription-login case the authentication page describes. It does not switch the active account when a higher-precedence credential is set: Bedrock, Vertex, Foundry, gateway, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, `apiKeyHelper`, `CLAUDE_CODE_OAUTH_TOKEN`, or a named Anthropic profile.
- On macOS, a locked-Keychain login now lives in `~/.claude/.credentials.json`. A switcher that only writes the Keychain item leaves that fallback in place, and Claude Code will keep reading it.
- `CLAUDE_CONFIG_DIR` is both a second Keychain entry and a second transcript root. Keyhop's macOS credential path uses the service name `Claude Code-credentials` and `~/.claude.json` in the home directory, and its transcript reader is rooted at `~/.claude/projects` (checkout: `ClaudeAdapter.swift`, `LogFeeds.swift`). Those readers miss a non-default config directory and the macOS file fallback.
- A keyless Console sign-in signs out the claude.ai login and stores a profile under `~/.config/anthropic`. Calling `/logout` to clear it revokes that credential. A file-level switcher should leave profiles alone unless it is prepared to revoke.
- Transcript slug rules changed in the 2.1.224 line for long paths, and the line schema is explicitly unstable. Counting `usage` on `type: assistant` lines still matches the documented JSONL location, and any parser can break on a release. `claude -p` / Agent SDK lines in that tree may bill the post-15-June-2026 Agent SDK credit rather than the interactive 5-hour and weekly windows.
- The 5-hour and weekly windows are still the documented subscriber limits. The new fields a limit display can miss are the Opus-only limit and usage credits. The status-line payload does not carry credits, so a 100% weekly figure can mean "now spending credits" rather than "blocked."

### Gaps
- The authentication page never names the Keychain service `Claude Code-credentials`, the account attribute, `claudeAiOauth`, `mcpOAuth`, or `oauthAccount` in `~/.claude.json`. 2026 GitHub issues still show `claudeAiOauth` inside `Claude Code-credentials`. Whether `CLAUDE_CONFIG_DIR` changes the service name, the account name, or an extra attribute is not specified.
- No official page fetched here documents `https://api.anthropic.com/api/oauth/usage` or the keys `seven_day_opus` and `seven_day_sonnet`. The errors page confirms an Opus limit exists; it does not give the JSON field name.
- No Anthropic page fetched here confirms a 6 May 2026 doubling of 5-hour limits. That claim appears on a secondary blog ([morphllm](https://www.morphllm.com/claude-code-usage-limits)) and was not treated as fact.
- The archived help-center hour estimates (for example "40–80 hours of Sonnet 4") are older material and disagree with the current errors page, which publishes reset behavior and plan sharing, not fixed weekly hours. — [Archive](https://archive.ph/G51jH)

## Did Codex CLI change auth.json shape, add ChatGPT-plus-API-key accounts, or expose a usage/quota API a third party can call?

### Takeaway
`~/.codex/auth.json` (or the OS credential store) is still the cache, and it now holds exactly one of ChatGPT, an API key, or a Codex access token. Official docs do not publish the JSON shape and do not offer an HTTP usage API for third parties. They tell automation to let Codex refresh `auth.json` itself. A local app-server method for rate limits shows up in 2026 GitHub issues, not in the auth page.

### Cited Findings
- Two sign-in methods for OpenAI models: ChatGPT (subscription, included plan credits) and an API key (standard API pricing). CLI, IDE extension, and ChatGPT desktop app share one cached login. Codex cloud is ChatGPT-only. API-key CLI login is `printenv OPENAI_API_KEY | codex login --with-api-key`. ChatGPT CLI login is `codex login`. `codex login status` reports the method. `codex logout` clears stored credentials. When workload identity is selected, `codex login` and `codex logout` are rejected. — [Authentication](https://developers.openai.com/codex/auth)
- A third stored method for Enterprise automation: `printenv CODEX_ACCESS_TOKEN | codex login --with-access-token`. Access tokens are for ChatGPT workspace entitlements without a browser. They are not Platform API keys. API keys and Codex access tokens do not enable Work Cloud local computer access. — [Authentication](https://developers.openai.com/codex/auth)
- Cache location: plaintext `~/.codex/auth.json`, or the OS credential store. `cli_auth_credentials_store` is `file` (`auth.json` under `CODEX_HOME`, default `~/.codex`), `keyring` (OS store, fails if unavailable), `auto` (OS store, else `auth.json`), or `ephemeral` (memory for the current process). Admins can force `cli_auth_credentials_store` and `chatgpt_base_url`. `forced_login_method` is `"chatgpt"` or `"api"`; `forced_chatgpt_workspace_id` pins a workspace. If the active credentials do not match, Codex logs the user out and exits. — [Authentication](https://developers.openai.com/codex/auth)
- Headless fallback still copies `~/.codex/auth.json`. Device-code login is `codex login --device-auth` (beta). ChatGPT sessions refresh tokens automatically during use. The same page says the supported CI pattern is to let Codex refresh `auth.json` and keep the updated file, and that API keys remain the default for automation. — [Authentication](https://developers.openai.com/codex/auth)
- CI/CD guide (ChatGPT-managed auth, `auth_mode: "chatgpt"`): Codex loads `auth.json`; if `last_refresh` is older than about 8 days it refreshes and writes new tokens and a new `last_refresh`; a 401 also refreshes and retries. The guide says the supported strategy is not to call the refresh API yourself. Only one machine or serialized job stream should use a given copy. Rewriting the file from the original secret on every run throws away the refreshed tokens. — [Maintain Codex account auth in CI/CD](https://learn.chatgpt.com/docs/auth/ci-cd-auth)
- Custom model providers: `requires_openai_auth = true` uses the ChatGPT or API-key cache and ignores `env_key`. Otherwise `env_key` reads a provider API key from the environment, and `auth.json` is not the login store. An older maintainer comment on CLI 0.35.0 (issue opened against 0.30.0) already said a custom provider does not use `auth.json`, that `preferred_auth_method` was removed, and that `/logout` deletes `auth.json`. The current flag is `--with-api-key` on stdin, not the `--api-key` form in that comment. Treat the issue as older than the current auth page. — [Authentication](https://developers.openai.com/codex/auth); [Issue 3286](https://github.com/openai/codex/issues/3286)
- Local state under `CODEX_HOME`: `config.toml`, `auth.json` or the OS keyring, `history.jsonl` when history persistence is on, plus logs and caches. History default is session transcripts at `$CODEX_HOME/history.jsonl` (example `~/.codex/history.jsonl`); `history.persistence = "none"` disables it. `sqlite_home` is a SQLite state DB for agent jobs and resumable runtime state. The config reference does not name `sessions/`, `archived_sessions/`, `rollout-*.jsonl`, or `token_usage_record`. — [Advanced configuration](https://developers.openai.com/codex/config-advanced); [Configuration reference](https://developers.openai.com/codex/config-reference)
- `codex resume` and `codex exec resume` accept `--last` for the most recent session in the current working directory, or `--all` to search every directory. The resume docs do not say a running process keeps the previous account until resume. — [CLI reference](https://developers.openai.com/codex/cli/reference)
- `/status` shows session configuration and token usage. `/statusline` can show rate limits. `memories.min_rate_limit_remaining_percent` defaults to 25 and gates memory generation on remaining rate-limit capacity. None of these pages document an HTTP quota API or the JSON of `auth.json` beyond the CI guide's `auth_mode` and `last_refresh`. — [Slash commands](https://developers.openai.com/codex/cli/slash-commands); [Configuration reference](https://developers.openai.com/codex/config-reference)
- 2026 GitHub issues describe a local JSON-RPC method on `codex app-server`: `account/rateLimits/read`. Reported fields include `primary` and `secondary` windows with `usedPercent`, `windowDurationMins` (300 and 10080 in the samples), `resetsAt`, `credits`, and `planType`. One report on CLI 0.146.0 says only the 10080-minute window came back for that account, so the 5-hour window was missing. These are issue reports, not an OpenAI docs page. — [Issue 24080](https://github.com/openai/codex/issues/24080); [Issue 20310](https://github.com/openai/codex/issues/20310)
- Source commit, not a user-facing doc: keyring-mode CLI auth can store the payload in an encrypted local-secrets file because Windows Credential Manager limits generic credentials to 2,560 bytes and large ChatGPT auth payloads can exceed that. The commit says successful encrypted saves remove stale `auth.json` fallback data, and logout removes encrypted, direct-keyring, and fallback data. It does not, in the commit message, name the secrets file path. The auth page fetched the same day still says keyring means "your operating system credential store" and does not mention an encrypted sidecar. — [Commit 56c97e3](https://github.com/openai/codex/commit/56c97e3b5c8430613afc6d782ab7463bce8df812); [Authentication](https://developers.openai.com/codex/auth)
- Non-interactive `--json` stdout includes `turn.completed` with `usage.input_tokens`, `cached_input_tokens`, `output_tokens`, and `reasoning_output_tokens`. That is a live stream, not a documented on-disk transcript schema. — [Non-interactive mode](https://developers.openai.com/codex/noninteractive.md)

### Inferences
- There is no combined "ChatGPT plus API key" account in one file. The cache is one login: ChatGPT, API key, or Codex access token. Keyhop's "ChatGPT sign-ins only" rule still matches a real split, and it now misses two stored login types the CLI will actually run: API keys and access tokens. Replacing `auth.json` can switch them only when `cli_auth_credentials_store` is `file`.
- `keyring`, `auto`, and `ephemeral` mean a rewrite of `auth.json` is not the live credential. The commit says a successful encrypted save deletes the stale `auth.json` fallback, so a later file write can also be discarded or can fight logout's cleanup.
- Keyhop refreshes ChatGPT tokens itself and writes `last_refresh` (`CodexAdapter.swift`). The CI guide says a third party should not call the refresh endpoint, and that two writers of the same `auth.json` drop rotated refresh tokens. That is the same class of single-use refresh loss as Claude Code issue 88583. `codex logout` and a `forced_login_method` mismatch clear the login; a switcher that shells out to logout will drop the token it just stored. The docs say "clears," not "revokes at the server."
- Official transcript path for counting is `history.jsonl` under `CODEX_HOME`. Keyhop counts `~/.codex/sessions/**/rollout-*.jsonl` and `~/.codex/archived_sessions`, and those roots ignore `CODEX_HOME` (`LogFeeds.swift`). The docs fetched here do not confirm or retire the rollout files. If they still exist, a non-default `CODEX_HOME` is invisible to Keyhop. If Codex moved token records into `history.jsonl` only, Keyhop's reader is looking at the wrong files. That second possibility is not established.
- `account/rateLimits/read` is a local CLI RPC a process can call, not a documented HTTP API. It is the closest 2026 quota surface. Window lengths in samples are still 5 hours (300 minutes) and 7 days (10080 minutes), with a report that the 5-hour window can be absent. Keyhop's `https://chatgpt.com/backend-api/wham/usage` call is not described on the pages fetched here.

### Gaps
- No official page states the `auth.json` keys (`tokens`, `id_token`, `account_id`, API-key field names). Only `auth_mode: "chatgpt"` and `last_refresh` appear, on the CI guide.
- No official page names `sessions/`, `rollout-*.jsonl`, `token_usage_record`, or `token_count`.
- No official page says whether a running `codex` process re-reads `auth.json` or keeps the old account until `codex resume --last`.
- The encrypted secrets file path is not in the commit message or the auth page.
- No date on commit 56c97e3 was captured here. The auth page that omits the sidecar was fetched 3 October 2026.

## Did GitHub Copilot or gh change multi-account switching, or start writing a local usage transcript? What about Copilot CLI vs the editor?

### Takeaway
`gh auth switch` is still the supported way to change the active GitHub account, and `gh auth logout` still drops a token. Copilot CLI now has its own login, its own `~/.copilot` tree, and a session event log that can carry shutdown usage totals. Per-call token events are ephemeral. The editor still has no documented local model-token transcript. Plan quota remains an account-level allowance, with AI credits alongside premium requests in the 2026 SDK.

### Cited Findings
- `gh auth switch` changes the active account for a host. Two accounts on a host switch automatically; more than two need `--user` or a prompt. `--hostname` and `--user` disambiguate non-interactive use. `gh auth status` lists accounts. — [gh auth switch](https://cli.github.com/manual/gh_auth_switch)
- Multiple-account design, `cli/cli` trunk doc: `auth login` is additive; `auth switch` swaps the token `gh` uses for API and for git when `gh` is the credential helper. `auth logout` switches to a remaining account when the active user is the one logged out. `auth token`, `auth switch`, and `auth logout` take `--user`. The doc explicitly points `gh auth token --user` at automated switching. It says logout of one account among several switches rather than leaving the host with no token. — [multiple-accounts.md](https://github.com/cli/cli/blob/trunk/docs/multiple-accounts.md)
- Copilot CLI auth order: `COPILOT_GITHUB_TOKEN`, then `GH_TOKEN`, then `GITHUB_TOKEN`, then an OAuth token from the system keychain, then `gh auth token` as the lowest-priority fallback, used only when no environment token and no stored Copilot token exist. An environment token overrides the stored OAuth token from `copilot login`. Classic `ghp_` PATs are not supported. Fine-grained PATs need the "Copilot Requests" permission. `copilot login --with-token` reads a token from stdin and conflicts with `--web-flow` and `--device-code`. In-session account switch is `/user switch`. — [Authenticate Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/authenticate-copilot-cli); [CLI command reference](https://docs.github.com/en/copilot/reference/cli-command-reference)
- Copilot CLI config directory is `~/.copilot` (`$HOME/.copilot`). `config.json` holds application state, including authentication and `loggedInUsers`. User settings moved from `config.json` to `settings.json`; `loggedInUsers` stays in `config.json`. `session-state/<session-id>/` holds an event log `events.jsonl` plus plans, checkpoints, and tracked files, used for `--resume` and `--continue`. `session-store.db` is SQLite for cross-session data. Deleting `session-state` removes local copies only; sessions synced to the GitHub account are a separate store. The page does not list event types inside `events.jsonl`. — [CLI configuration directory](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-config-dir-reference); [CLI best practices](https://docs.github.com/en/copilot/how-tos/copilot-cli/cli-best-practices)
- SDK, current docs: `assistant.usage` is one event per model API call, with `model`, `inputTokens`, `outputTokens`, cache and reasoning fields, and a premium-request `cost`. It is ephemeral and is not replayed on resume. Durable reads are RPC `session.usage.getMetrics` (`totalNanoAiu`, `totalPremiumRequestCost`, per-model `usage.inputTokens` / `usage.outputTokens`). `account.getQuota` returns `quotaSnapshots`, commonly keyed `premium_interactions`, `chat`, and `completions`, with `entitlementRequests` (`-1` means unlimited), `usedRequests`, `remainingPercentage`, and `resetDate`. `getQuota` can take a specific user's GitHub token. `session.usage.getMetrics` is marked experimental. — [Usage and billing metrics](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/usage-and-billing); [Streaming session events](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/streaming-events)
- Streaming schema also defines `session.usage_checkpoint` (durable aggregate: `totalNanoAiu`, optional `totalPremiumRequests`) and `session.shutdown` (`totalPremiumRequests`, `totalApiDurationMs`, `modelMetrics`, `codeChanges`). `session.usage_info` is context-window size, not billing, and the generated types mark it ephemeral. — [Streaming session events](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/streaming-events)
- `github/copilot-cli` issue 1394 asked for premium-request and per-model token stats to be written because they were only printed at exit. A comment says that around the beginning of March 2026, `session.shutdown` in `events.jsonl` gained `modelMetrics` and `totalPremiumRequests`, and a later comment says the issue is fixed, including across resume. The comment's example path is `~/.copilot/session-state/.../events.jsonl`. That is an issue thread, not the config-directory page. — [Issue 1394](https://github.com/github/copilot-cli/issues/1394)
- Billing: the legacy premium-request article applies only to Copilot Pro and Pro+ subscribers on an existing annual plan who stayed on legacy premium-request billing after 1 June 2026. On that plan, Copilot Chat in an IDE uses one premium request per user prompt times the model rate, and each Copilot CLI prompt uses one premium request with the default model, times the model rate otherwise. Included amounts on that page: Pro 300/month, Pro+ 1500/month, reset on the 1st at 00:00:00 UTC. The SDK page treats AI credits (`totalNanoAiu`, divided by 1e9 in the examples) and premium-request cost as separate figures, and says the conversion is defined by Copilot billing, not by the SDK. — [Requests in GitHub Copilot (legacy)](https://docs.github.com/en/copilot/reference/copilot-billing/request-based-billing-legacy/copilot-requests); [Usage and billing metrics](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/usage-and-billing)
- Chronicle stores CLI session data locally and, by default, syncs it to the GitHub account. `/chronicle cost tips` talks about token spend. The chronicle page does not name a file path or a per-call token schema. — [Using Copilot CLI session data](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/chronicle)

### Inferences
- `gh auth token`, `gh auth switch`, and `gh auth login --with-token` are still the right switch surface for the GitHub account, and still the right way to avoid rewriting `hosts.yml`. `gh auth logout` still removes a login (and, with other accounts present, switches the active one). A switcher that must not revoke tokens should keep refusing logout.
- Copilot CLI no longer means "whatever `gh` is using." Its own keychain OAuth and `COPILOT_GITHUB_TOKEN` / `GH_TOKEN` / `GITHUB_TOKEN` win over `gh auth token`. Switching `gh` changes the editor and `gh`-backed tools, and changes Copilot CLI only when the CLI has no higher-priority credential. `/user switch` and `copilot login --with-token` are a second switch path. `config.json` `loggedInUsers` is a second account list.
- The editor still has no documented local token transcript. CLI `events.jsonl` is a session log for resume. Official docs say per-call `assistant.usage` is not stored. Shutdown and checkpoint events are the durable usage records, and issue 1394 says shutdown totals are now in `events.jsonl`. That is aggregate premium requests and per-model token totals at shutdown, not a complete per-request transcript of the kind Claude Code writes on every assistant message. Counting those lines would extend Keyhop for Copilot CLI only, and would miss the editor, cloud agent, and any call whose usage stayed in an ephemeral event.
- `account.getQuota` still speaks `premium_interactions`. It is an SDK RPC against a running Copilot client, not a new public REST shape. It does not replace reading plan quota, and it does not by itself provide token history.
- After 1 June 2026, "premium requests" are the legacy meter for a subset of annual plans. AI credits are the unit the SDK tells integrators to display. A UI that only shows a premium-request remainder can describe the wrong pool for accounts that moved off legacy billing.

### Gaps
- No 2026 page fetched here states the `hosts.yml` path or schema. The multiple-accounts doc describes commands, not files. No evidence found that `gh` stopped using `~/.config/gh/hosts.yml` or `$GH_CONFIG_DIR`.
- The config-directory page does not say which event types are persisted in `events.jsonl`. Persistence of `session.shutdown` / `modelMetrics` rests on issue 1394.
- No page fetched here says the VS Code, JetBrains, or other editor extensions write `~/.copilot/session-state` or any other model-token log.
- The non-legacy billing article (the successor to premium requests for everyone else) was not fetched. The legacy page and the SDK page disagree in emphasis: one is premium requests, the other is AI credits plus premium-request cost.
- No page says `gh auth logout` revokes the token at GitHub rather than only deleting the local credential. The CLI doc says logout removes that account and can switch to another. Keyhop's reason for never calling it (revoke) is stronger than what these pages state, and the safe behavior is still to avoid logout because it deletes the login.

## Which of these are real gaps for a switcher that must not revoke tokens?

### Takeaway
The dangerous gaps are credentials that outrank the file Keyhop swaps, refresh races that destroy a token Keyhop did not mean to revoke, and logout commands that delete or revoke a login. Copilot CLI's own token store is the largest switching miss. Copilot CLI's shutdown usage events are the only new transcript worth counting, and they are not a full token history.

### Cited Findings
- Claude `/logout` on a keyless Console sign-in removes and revokes that credential. Claude Code itself signs the machine out of claude.ai when that Console sign-in is created. — [Authentication](https://code.claude.com/docs/en/authentication)
- A failed Claude refresh can overwrite `claudeAiOauth` with empty tokens (`expiresAt: 0`) so the refresh token is gone and only interactive `/login` recovers. MCP and claude.ai OAuth still share one Keychain blob; MCP write corruption of that blob was fixed in v2.1.136, and the claude.ai refresh race is described after that fix. — [Issue 88583](https://github.com/anthropics/claude-code/issues/88583); [Issue 45551](https://github.com/anthropics/claude-code/issues/45551)
- Codex: do not call the refresh API yourself; two users of one `auth.json` drop rotated tokens. `codex logout` clears stored credentials, including encrypted and keyring copies in the source commit. A `forced_login_method` mismatch logs the user out and exits. — [CI/CD auth](https://learn.chatgpt.com/docs/auth/ci-cd-auth); [Authentication](https://developers.openai.com/codex/auth); [Commit 56c97e3](https://github.com/openai/codex/commit/56c97e3b5c8430613afc6d782ab7463bce8df812)
- `gh auth logout` removes the targeted account and switches to another account on that host if one remains. `gh auth token --user` is the documented non-interactive read. — [multiple-accounts.md](https://github.com/cli/cli/blob/trunk/docs/multiple-accounts.md)
- Anthropic's legal page forbids third-party products from offering Claude.ai login or routing requests through Free, Pro, or Max credentials on behalf of users. — [Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)
- Copilot CLI keychain OAuth and env tokens outrank `gh auth token`. — [Authenticate Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/authenticate-copilot-cli)

### Inferences
- Real switching gaps, in order:
  1. Claude credentials that are not `claudeAiOauth`: API key, `CLAUDE_CODE_OAUTH_TOKEN`, `apiKeyHelper`, Bedrock, Vertex/Agent Platform, Microsoft Foundry, gateway, and Anthropic profiles in `~/.config/anthropic`. Also the macOS Keychain-locked fallback file, and a Keychain entry keyed to `CLAUDE_CONFIG_DIR`. Touching profiles or calling `/logout` can revoke.
  2. Codex logins that are not a ChatGPT `auth.json`: API-key login, access-token login, and `keyring` / `auto` / `ephemeral` storage. Rewriting `auth.json` while Codex or Keyhop refreshes the same refresh token can invalidate the copy still on disk. Do not call `codex logout`.
  3. Copilot CLI does not follow `gh auth switch` once it has its own token. Switching `gh` still matches the editor and `gh`. Adding a Copilot CLI switch means `copilot login` / `/user switch`, never `gh auth logout` or `copilot` logout if that command deletes the token. The pages fetched here document `/login` and `/user switch`, not a Copilot logout command.
- Real metering gaps:
  1. Claude transcript root and slug algorithm (`CLAUDE_CONFIG_DIR`, 200-character hash, `CLAUDE_CODE_PROJECT_DIR_NAME`, skipped history). Opus limit and usage credits are extra limit fields. Agent SDK / `claude -p` usage is a separate pool after 15 June 2026, while the JSONL files still sit in the same tree.
  2. Codex on-disk token history is not documented at the rollout path Keyhop reads. `history.jsonl` under `CODEX_HOME` is the documented transcript. No documented third-party HTTP quota API; the app-server rate-limit read is local and unofficial as a public contract.
  3. Copilot editor: still no local token transcript. Copilot CLI: `events.jsonl` shutdown totals are a new partial transcript (premium requests and per-model tokens at session end). Per-call `assistant.usage` is explicitly not persisted. Quota is still plan-level (`premium_interactions` and, in the SDK, AI credits), not something to reconstruct from editor logs.
- Refreshing a Claude or Codex OAuth token in order to read quota is the action both vendors warn will rotate or destroy the only refresh token. Doing that refresh for an account that is also logged in inside a live CLI is the scenario that blanks `claudeAiOauth` or strands `auth.json`.

### Gaps
- No source fetched here states that `gh auth logout` or `codex logout` revokes the token on the server. Claude's keyless Console `/logout` does say revoke. The switcher rule "never logout" is still the one that matches the destructive local behavior all three document.
- Whether Keyhop's existing calls to Claude's OAuth usage endpoint and ChatGPT's `wham/usage` endpoint are still accepted was not re-tested on 3 October 2026. Those URLs are not in the official docs fetched here. Anthropic's legal page is the policy constraint on using claude.ai credentials from a third-party app.
