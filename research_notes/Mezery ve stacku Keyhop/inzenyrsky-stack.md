# Engineering stack gaps for Keyhop (as of 3 October 2026)

Scope is the stack this checkout already runs: Workers + D1 (`cloud/wrangler.jsonc`, `compatibility_date` `2026-08-22`, flat SQL in `cloud/migrations/`, hourly cron `17 * * * *`), a local stdio MCP server pinned to protocol `2025-11-25` (`Sources/Keyhop/CLI/MCPServer.swift`), and npm `e2e` `0.15.2` plus `@e2e-dev/web` `0.11.1` (lockfile). ## What changed in Cloudflare Workers or D1 in 2026 that this kind of app should adopt or avoid?

### Takeaway
Adopt almost nothing from the 2026 Workers/D1 changelog. The one behavior change that can break keyhop.app is hard failure of D1 queries on the Workers Free plan after 1 September 2026. Nested migrations, a US jurisdiction, Worker Previews, Workflows, Artifacts, and the Agents/Pi harness are mismatches for the existing database and request path.

## What is the current MCP spec status (authorization, elicitation, apps), and which should a read-only local stdio server ignore versus adopt?

### Takeaway
`2026-07-28` is the released spec: stateless core, optional `server/discover`, and a formal extensions framework. A read-only local stdio server should ignore authorization, elicitation, and MCP Apps. The only protocol gap in Keyhop's server is that it still speaks the `2025-11-25` `initialize` handshake and has no `server/discover`. Current clients are specified to fall back when that probe fails.

### Cited Findings
- The `2026-07-28` specification is released, with updated TypeScript, Python, Go, and C# SDKs. It removes the required `initialize` / `initialized` handshake and the `Mcp-Session-Id` header from the core. Each request carries protocol version, client identity, and capabilities. `server/discover` is optional. Tasks left the experimental core and became the `io.modelcontextprotocol/tasks` extension. MCP Apps and Enterprise Managed Authorization are extensions. Dynamic Client Registration is deprecated in favor of Client ID Metadata Documents and remains for compatibility. Clients must validate the RFC 9207 `iss` parameter on authorization responses. — [2026-07-28 release post](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- Authorization is optional. HTTP transports SHOULD follow the authorization spec. STDIO transports SHOULD NOT, and SHOULD take credentials from the environment instead. — [Authorization, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization); same rule in the [base spec](https://modelcontextprotocol.io/specification/2026-07-28/basic)
- The HTTP authorization changes in that release (issuer validation, `application_type` on Dynamic Client Registration, credentials bound to an issuer, refresh-token notes, scope accumulation, `.well-known` suffix) apply to remote OAuth, not to a process launched on stdin. — [Release candidate notes](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/); [Cloudflare's summary of the same release](https://blog.cloudflare.com/mcp-v2/)
- On stdio, metadata lives in the JSON-RPC body under `_meta.io.modelcontextprotocol/*`. There is no header layer. The server must not write anything but MCP messages to stdout, and must not send JSON-RPC requests. Server-to-client questions travel as `InputRequiredResult` replies. A client that speaks both eras SHOULD probe with `server/discover` first. A `DiscoverResult` means a modern server. An `UnsupportedProtocolVersionError` means modern but wrong version, and the client must not fall back. Any other error, or a timeout, means a legacy server, and the client falls back to `initialize`. The fallback must not depend on one error code, because legacy servers commonly return `-32601` or `-32602`. A modern-only client does not have to probe, but probing is still recommended. — [stdio transport, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio)
- Elicitation has form mode and URL mode. Servers MUST NOT use form mode for passwords, API keys, access tokens, or payment credentials. URL mode is for those sensitive out-of-band steps. URL mode is not how an MCP client authorizes itself to the MCP server; that is the authorization spec. Servers MUST NOT use URL elicitation to authorize users for themselves. The client's bearer token does not change. URL mode was introduced in the `2025-11-25` revision. Clients declare `elicitation` on each request; a server must not send a mode the client did not declare. — [Elicitation, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation)
- MCP Apps is an optional extension, identifier `io.modelcontextprotocol/ui`, stable spec date `2026-01-26` (SEP-1865 status Final). It serves HTML in a sandboxed iframe via `ui://` resources linked from tool metadata. Hosts and servers must negotiate it. Existing servers keep working if they do not. — [ext-apps spec 2026-01-26](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx); [SEP-1865](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp.md); [extensions mentioned in the 2026-07-28 release](https://blog.modelcontextprotocol.io/posts/2026-07-28/)

### Inferences
- Local checkout: `MCPServer` advertises `2025-11-25` and also accepts `2025-06-18` and `2024-11-05`. It handles `initialize`, `ping`, `tools/list`, and `tools/call`. Anything else, including `server/discover`, gets JSON-RPC `-32601`. That is the error the stdio spec says should make a dual-era client fall back to `initialize`. Keyhop therefore still works with clients that implement that fallback. A client that only speaks `2026-07-28` and skips the probe would not.
- The server already sets `readOnlyHint`, `destructiveHint: false`, `idempotentHint`, and `execution.taskSupport: "forbidden"`. Leaving Tasks unimplemented matches a short local read. Do not add the tasks extension.
- Ignore authorization (OAuth, CIMD, DCR, protected-resource metadata, Workers OAuth Provider). The spec says stdio should not implement it. The tools read the local Keyhop workspace. There is no remote resource server.
- Ignore elicitation. The tools do not need a secret, a payment, or a third-party OAuth grant mid-call. Asking for account tokens through form mode would violate the spec. URL mode would be the wrong tool for "authorize the MCP client," which this server does not need.
- Ignore MCP Apps. The product UI is the Mac window and keyhop.app. A chat iframe would duplicate those surfaces and is optional.
- Worth adopting only if a host drops the legacy fallback: answer `server/discover` and accept `2026-07-28` per-request metadata, while still answering `initialize` for the clients listed in the server today. That is a compatibility implementation, not a new product tool.
- The assignment listed three tools. This checkout registers four: `keyhop_status`, `keyhop_usage`, `keyhop_recommendation`, and `keyhop_services` (`openWorldHint: true`, public status pages). The fourth tool does not change the auth/elicitation/apps decision.

### Gaps
- This research did not check whether current Claude, Cursor, or Codex clients still fall back to `initialize` after a `-32601` from `server/discover`, or whether any of them are already modern-only. The spec describes the fallback; host behavior was not tested.
- No Swift MCP SDK release that speaks `2026-07-28` was reviewed. The server is hand-rolled JSON-RPC.
- Whether `execution.taskSupport` is a legal field on a `2025-11-25` `tools/list` result was not checked against the older schema. It is present in this checkout.

### Cited Findings

## Any Swift or notarization change in 2026 that changes how an unsigned Mac app should ship?

### Takeaway
No 2026 Apple notarization document changes the shipping recipe for an app that is already unsigned and not notarized. Gatekeeper on current macOS still blocks quarantined unsigned code, including when "Anywhere" is enabled. That constraint was re-tested in August 2026; it is not a new notarization API. No 2026 Swift language change that alters this was found.

### Cited Findings
- Apple's notarization document still says: from macOS 10.14.5, software signed with a new Developer ID and new kernel extensions must be notarized; from macOS 10.15, all software built after 1 June 2019 and distributed with Developer ID must be notarized. Mac App Store distribution is exempt because review already covers it. The notary service scans for malware and code-signing issues and returns a ticket to staple. The page recommends notarizing older and even unsigned preexisting software, and says the service may relax rules for that older software using telemetry. It does not describe a 2026 rule change. — [Notarizing macOS software before distribution](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)
- `altool` has been rejected by the notary service since 1 November 2023. The supported upload path remains `notarytool`. That is not a 2026 change. — [Customizing the notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)
- The user-facing Control-click "Open" override for unsigned or non-notarized software was removed in macOS Sequoia. Apple said that on 6 August 2024. Users were told to approve the last blocked app in System Settings, Privacy & Security. — [Ars Technica, 6 Aug 2024](https://arstechnica.com/gadgets/2024/08/macos-15-sequoia-makes-you-jump-through-more-hoops-to-disable-gatekeeper-app-checks/)
- Howard Oakley, testing after `spctl --master-disable` stopped being supported, wrote on 11 August 2026: completely unsigned code has never been allowed on Apple silicon; a quarantined unsigned app stayed blocked even when Privacy & Security was set to Anywhere (the dialog was misleading and the app still did not open); executable code must be signed, ad hoc at minimum, and the signature must be intact; quarantined code can run with Anywhere enabled only when it is signed and not notarized; adding the app as a Developer Tool does not clear quarantine; "Anywhere" does not disable Gatekeeper or on-demand XProtect. — [Eclectic Light Company, 11 Aug 2026](https://eclecticlight.co/2026/08/11/how-can-you-run-code-that-hasnt-been-notarised/)
- macOS Tahoe 26.6's security notes include two Gatekeeper-related fixes: "An app may bypass Gatekeeper checks" (logic issue, improved checks) and a DesktopServices "file quarantine bypass" (additional checks). These close bypasses. They do not document a new developer upload flow. — [About the security content of macOS Tahoe 26.6](https://support.apple.com/en-us/128067)
- Apple's current "Safely open apps on your Mac" article still states that macOS checks the Developer ID signature of software from outside the App Store, and that Catalina and later also require notarization by default. It warns that unsigned, non-notarized software can expose the machine to malware. The fetched snippets do not add a 2026-only distribution step. — [Apple Support HT102445](https://support.apple.com/en-us/102445)

### Inferences
- The concrete product gap is unchanged by 2026 paperwork: a downloaded (quarantined) Keyhop build that is not Developer ID-signed and notarized still depends on the user finding the one-shot approval in Privacy & Security, and a completely unsigned Apple silicon binary still does not run. Ad hoc signing is the minimum Oakley found for Apple silicon, and it does not by itself satisfy Gatekeeper for a quarantined download the way a stapled Developer ID ticket does.
- Tahoe 26.6 is a reason not to document a Gatekeeper or quarantine bypass as the install path. Apple patched bypasses in that release. It is not a reason to expect a new notary flag or a Swift compiler switch.
- No Swift 6.x or Xcode release note reviewed here changes codesign, stapling, or the unsigned-download path. Notarization remains `codesign` plus `notarytool` plus `stapler`, for a Developer ID app linked against the 10.9 SDK or later with the hardened runtime. That recipe is older than 2026.

### Gaps
- No 2026 Swift evolution proposal or Xcode release note was fetched. Absence here means this pass did not find one, not that none exists. A general "turn on Swift 6" note would not change how the unsigned app is shipped.
- How the Keyhop Mac binary is actually signed (unsigned versus ad hoc versus Developer ID) was not read from the packaging scripts. The assignment states it is not notarized. Oakley's split between "unsigned" and "ad hoc but not notarized" matters on Apple silicon, and this pass cannot say which of those two the shipped artifact is.
- A secondary page claimed macOS Tahoe's user guide limits the "Open Anyway" button to about an hour. That claim is not in the Apple Support article cited above, and it was not confirmed against an Apple user-guide URL. It is not treated as a fact.
- Linux (Python GTK 3 tray) and the iOS app's absence from the App Store were outside the notarization question. No 2026 Apple notarization change covers those surfaces.
